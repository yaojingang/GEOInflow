# 可选 ClickHouse 历史日志分析

默认部署使用 PostgreSQL、现有汇总及 Redis。可选 ClickHouse 保存可重建的日志分析投影，分担历史聚合；PostgreSQL 继续保存原始日志、账号、权限、事务、证据和管理状态。启用后总存储占用会增加。

## 安装与管理

本地配套安装使用 `sh scripts/liekan-deploy.sh --with-clickhouse`。服务固定为 ClickHouse 26.8.34.13，预算为额外 2 CPU、4 GiB 内存，使用独立数据卷及内部网络。安装器生成独立随机密码，写入私有 `.env`，后续默认部署会识别并保留该服务、配置和数据卷。已有卷缺少原密码或原容器时停止升级，恢复原配置和容器后重试。

已有外部服务可设置 `LIEKAN_ANALYTICS_CLICKHOUSE_URL`，格式为 `https://用户名:密码@主机:端口/数据库`；对 URL 中的用户名、密码进行百分号编码。数据库名仅使用字母、数字和下划线。账户需要在该专用数据库内建表、读取、插入和删除投影的权限。本地配套密码使用 `LIEKAN_CLICKHOUSE_PASSWORD`。不要设置上游 `CLICKHOUSE_URL` 来启用本功能。

系统管理员完整登录后，进入“系统管理 → 存储与分析”：检查连接、准备数据、执行对账，再启用 ClickHouse 分析。状态包括当前模式、版本、后台心跳、每站覆盖与任务进度。普通网站用户沿用原统计页面。管理员权限被撤销后，管理 API 拒绝访问；任务发布继续复核权限。

## 查询范围

历史请求量、AI 抓取量、异常状态、趋势、爬虫、厂商和路径聚合可以使用 ClickHouse。完整查询时间窗及全部条件必须受支持且覆盖有效。缺口、实时尾部、明细、游标分页、导出、浏览器 PV/UV、收入、漏斗和回放继续使用现有 PostgreSQL 路径。

历史窗口最多 366 天，结束时间需早于已闭合且缓冲 30 秒的 UTC 小时。PostgreSQL 在同一报告快照内通过索引定位原始日志首尾，对无记录的首尾范围保留显式空区间依据。范围内的空小时也会构建覆盖。查询按当前网站权限、来源、身份核验、已生效修复和规则版本读取，保留原时间边界和时区。页面数使用精确去重。

ClickHouse 的非空代次需要与 PostgreSQL 发布的记录数匹配。副本丢失、还原不完整或缺少代次时，当前查询回退并登记重建，避免把丢失数据解释为空统计。

## 同步与恢复

原始写入和 32 路分桶修正标记在同一 PostgreSQL 事务提交。新增爬虫证据按其原日志时间定点失效；来源区间与已生效历史修复变更使用相应版本围栏。新规则不会补造历史证据。

分析 worker 复用现有后台准入，以 UTC 小时为工作单元，每批最多 2,000 条，逐批读回并检查 SHA-256。任务领取先持久化，外部读写在 PostgreSQL 锁之外进行；发布再次检查当前权限、输入版本、指纹、控制修订及有效租约。中断后继续检查或重建候选；四次失败后停止自动重试，管理员可在后台重试。

暂停同步或切回 PostgreSQL 立即停止使用分析副本，保留源数据、变更标记及数据卷。恢复后补齐并校验。连接中断时进入原有 PostgreSQL 缓存和任务预算；后台会探测连接恢复。单次查询的条件或资源预算错误仅影响该请求。

## 数据清理与连接变更

每个部署在 PostgreSQL 保存独立身份。ClickHouse 的读、写和清理都绑定该身份，允许多个部署共用外部数据库时保持副本隔离。

网站重置、删除或截断立即使覆盖失效，并保存需要清理的来源代次和目标连接。后台按原目标清理，跨连接的未完成清理会保留，管理员需要恢复对应原连接完成清理后再继续准备。凭据轮换保留同一目标身份。

已清理的来源代次边界持久保留，后台继续扫除旧工作进程迟到写入的失效代次。首次清理优先执行；同步期间，已完成清理的扫尾最多占每八次领取中的一次，保障有效网站同步继续推进。新来源代次受独立围栏保护。过期候选和退休代次经七天保留后分批回收，当前有效代次和活动候选受到保护。

ClickHouse 投影包含记录 ID、时间、路径、状态、爬虫及版本等分析字段，不复制原始 IP、完整 User-Agent。原始采集是否存在与统计资格继续保持各自口径。

## 验证

`pnpm test:analytics-engine` 创建带唯一归属标签的 PostgreSQL 与 ClickHouse 测试容器，端口随机绑定至 `127.0.0.1`，验证迁移重跑、同步、查询对照、权限、失效、重试、租约、连接恢复和清理。结束时仅删除本次创建的容器及匿名卷。

`pnpm test:analytics-engine -- --benchmark --rows 1000000` 或 `--rows 10000000` 使用明确命名的合成数据。先按现有预算构建 PostgreSQL 汇总，再准备 ClickHouse。在汇总正常完成时，关闭应用结果缓存，交替测量 30、90、365 天范围，每种引擎每范围 200 次，并核对全部结果。

如果 PostgreSQL 汇总触及容量上限，则保留该状态，以生产报告的 60 秒预算探测原查询。该场景记录单次探测及超时，ClickHouse 仍测量 200 次，并与合成生成器可独立计算的精确期望值逐项核对。此时不生成 PostgreSQL 的 p95，也不声称完成同条件的性能提升比例验收。实际覆盖、样本数、p50/p95/p99、构建用时和存储分别记录在 `.local/analytics-engine/`，不纳入 Git。冷计算与结果缓存命中需要分别解释。

基准还会比较关闭捕获与开启捕获并发回填时的单条提交 p50/p95/p99，以及每批 100 条的持续写入吞吐。应用报告快照和关闭 JIT 的设置与生产执行路径一致。全年覆盖参数分段传递，遵守 ClickHouse 默认 HTTP 字段大小限制。

基准测试通过表示数据一致性与执行流程通过。写入性能目标单列在报告的 `ingestion.gates` 中；需要同时检查 p95 增量与吞吐比例，测试通过本身不代表所有性能目标达标。

`LIEKAN_ENGINE_VISUAL=1 pnpm test:analytics-engine` 使用生产构建，在独立无头浏览器中检查中英文、桌面和手机布局、真实管理员认证及切换操作，同时运行 1 CPU / 512 MiB 的实际分析 worker，验证 6,000 条多批日志的发布和 OOM 状态。该检查需要先执行 `pnpm build:app`、`pnpm liekan:build-worker`，并使用可初始化数据库模块的构建环境。

这些结果用于本次硬件和数据分布，不外推为所有部署的容量或 PB 级性能承诺。正式发布仍执行项目发布门禁。
